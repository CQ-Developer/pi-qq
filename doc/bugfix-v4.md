# pi-qq v4 问题调研：手机 QQ 长期后台后收不到消息

> 状态：调研记录；已实现 QQ `/last` 命令，其余修复待定  
> 日期：2026-11-04  
> 涉及版本：pi-qq 1.3.2，`@tencent-connect/qqbot-nodejs` 1.0.5  
> 范围：QQ C2C 私聊

## 1. 问题描述

用户反馈：

1. 手机 QQ 长时间挂在后台；
2. 电脑上的 pi 一直正常运行；
3. 电脑没有休眠，也没有切换网络；
4. **短时间后台/息屏后立即打开，一切正常**；
5. **长时间不打开 QQ 后，再次打开收不到任何机器人消息**；
6. 此时无法判断任务是在运行、已经完成，还是已经失败。

关键对比是第 4、5 条：短时间后台正常，长时间后台失败。这说明问题与**手机端 QQ 进程/连接在后台存活的时间**高度相关，而不是电脑侧 pi 是否运行。

需要区分两个不同的链路：

- **入站**：手机发出的 `C2C_MESSAGE_CREATE` 是否到达 pi；
- **出站**：pi 生成的回复是否到达手机 QQ，并在聊天记录中可见。

当前没有拿到事故时间段的 `pi-qq-*.log`。本文的结论来自代码路径、QQ 官方文档、局部复现和用户描述，仍需现场日志确认。

### 1.1 当前状态

- pi-qq 当前版本为 `1.3.2`；已实现 QQ `/last` 命令，其余修复待定。
- 用户环境为：手机 QQ 长时间后台，电脑上的 pi 持续运行，电脑未休眠、未切换网络。
- 现象具有明显的**时间阈值**：短时间后台正常，长时间后台后失败。
- 当前工作区没有找到事故时段的 `pi-qq-*.log`；`~/.pi/agent/pi-qq.json` 虽为 `logLevel: debug`，但无法确认事故进程的 cwd。
- 已基本排除入站和手机客户端同步；后续确认 TUI 持续有新事件，剩余关键是“iPhone 后台离线期间的平台保存/补发”还是“relay/stream 停止推送”。

### 1.2 追加确认（2026-11-04）

用户进一步确认：

1. 长时间后台后重新打开 QQ，发一条新消息，**电脑 pi 的 TUI 能收到**；
2. 长时间后台期间好友发来的普通 QQ 消息，重开后**能正常显示**；
3. 用户认为 `/qq-test-md` 和 `/qq-test-stream` 也能看到，因此暂不做该项测试。

由此可以基本排除：

- 入站 WebSocket 整体失效（新消息能到 pi）；
- 手机 QQ 客户端的会话同步整体失效（好友消息能显示）。

问题范围缩小为：**任务在手机离线期间产生的机器人输出没有出现在手机上**，或者**任务本身在后台期间没有继续产生输出**（后续 1.4 已确认 TUI 一直有新事件，排除 agent 静默）。

需要区分“重开后触发测试能看到”和“手机后台期间发送、任务结束后再重开能看到”。前者只能证明实时链路正常，不能证明离线期间的消息被保存；第 3 条目前仍是假设，建议至少做一次“后台期间触发、结束前不打开手机”的对照。

### 1.3 再次确认（2026-11-04）

用户补充：

1. 失败发生时，电脑 TUI 里的 **agent 仍在运行**；
2. 重新打开 QQ 后发送新消息，**机器人会在 QQ 上回复**。

这意味着：

- 入站链路正常；
- 实时出站链路正常；
- 任务没有结束，因此问题不是“任务结束后的最终输出丢失”；
- 后续又确认 TUI 一直有新事件，因此 agent 并非静默；剩余可能是手机端离线期间消息未送达/未补发，或 relay/stream 停止推送；
- 无论哪种情况，用户都缺少“任务仍在运行/执行到哪一步”的反馈。

### 1.4 环境与现象确认（2026-11-04）

用户补充：

1. 手机是 **iPhone**；
2. 失败时 **TUI 一直有新事件**，可以确定有内容在持续输出；
3. 没有固定的工具或步骤，发生过很多次；
4. 只要手机 QQ 长时间挂后台就会断；
5. 用户没有查看日志，以上是根据现象描述；怀疑是 iPhone 把 QQ 的网络杀掉了。

这些信息基本排除了“agent 静默”：TUI 有新事件，说明 agent 仍在产出，`RunFeedback` 应该有内容要发。最符合的解释变成：

- iPhone 长时间后台后挂起/断开了 QQ 的网络；
- 期间 pi-qq 仍在发送，但手机没有收到；
- 重开后 QQ 能同步好友普通消息，但机器人消息没有补发；
- 新消息能到达 pi 并得到回复，说明实时链路恢复后是正常的。

仍需日志确认失败期间 `stream`/`outbound` 是否显示发送成功；如果日志显示流式失败或熔断，则还要并行排查 relay。

## 2. 结论摘要

| 优先级 | 可能原因                                                            | 置信度 | 与现象的匹配度                                         |
| ------ | ------------------------------------------------------------------- | ------ | ------------------------------------------------------ |
| P0     | iPhone 长时间后台后挂起 QQ 网络，期间机器人输出未送达手机，也未补发 | 高     | 短后台正常、长后台失败；好友消息能同步、机器人消息不能 |
| P0     | 没有“下次入站补发”机制：用户回来后无法获知离线期间的任务输出/状态   | 高     | 用户无法判断执行到哪一步                               |
| P1     | 后台期间只有流式输出，没有普通文本终态，离线客户端无内容可恢复      | 中     | 与机器人消息缺失、好友普通消息正常相符                 |
| P1     | Relay/stream 在长任务中停止推送（60 分钟 `msg_id` 失效或熔断）      | 中     | TUI 有新事件但手机无消息时需要排查                     |
| P1     | C2C 被动回复窗口被写成 5 分钟，超过后走主动消息；主动消息可被关闭   | 高     | 长任务结果或兜底文本丢失                               |
| P2     | 入站 WebSocket 静默失效（新消息已能到达，已排除）                   | 低     | 与“新消息能收到”不符                                   |
| P2     | 长离线不补发事件，且没有启用 `sessionPersistence`                   | 低     | 更符合进程重启或长时间断线                             |

**结合最新确认**：失败时 TUI 持续有新事件，说明 agent 没有静默、relay 应该有内容要发；重开后新消息有 QQ 回复，说明实时出站正常。最符合现象的组合是：

1. iPhone 在长时间后台后挂起 QQ 的网络；
2. 这期间 pi 仍在产生输出并发送，但手机没有收到；
3. 重开后 QQ 能同步好友的普通消息，但机器人消息/流式消息没有补发；
4. pi-qq 也没有在用户下一次入站时补发这段时间的状态或输出。

下一步最关键的是确认失败期间日志中的 `stream`/`outbound` 是否显示发送成功，以及好友普通消息与机器人消息的同步差异。

## 3. 当前实现

### 3.1 入站链路

1. SDK 通过 WebSocket 接收 `C2C_MESSAGE_CREATE`，调用 `bot.on("message")`。
2. `src/qq/qq-message-handler.ts` 做 C2C、allowlist、回复预算和内容解析。
3. `deps.pi.sendUserMessage(...)` 把内容送入 pi agent。
4. `src/relay/run-stream-relay.ts` 负责把 agent 事件转成 QQ 输出。

`src/qq/qq-bot.ts` 的连接状态只由三个事件驱动：

```ts
bot.on("ready", () => report("connected"));
bot.on("resumed", () => report("connected"));
bot.on("disconnected", ({ willReconnect }) => report(willReconnect ? "reconnecting" : "stopped"));
```

没有心跳 ACK 年龄、最后入站时间或主动健康检查。

### 3.2 出站链路

QQ 任务输出默认走 `/v2/users/{openid}/stream_messages`：

- `src/relay/bubble-writer.ts` 负责切泡、追加和 `DONE`；
- `src/relay/stream-session.ts` 负责流式帧的重试、节流和断点续写；
- `src/relay/run-stream-relay.ts:197` 用 `ok && hasPushed` 判断流式是否已经接管输出；
- `index.ts:243-247` 一旦 `streamTookOver === true`，就**不再发送普通文本消息**。

关键假设是：流式帧 HTTP 成功就代表用户最终能看到内容。代码没有客户端投递确认，也没有在流式成功后补发普通文本。

### 3.3 状态显示

`index.ts:70` 的连接状态来自缓存的 `lastState`：

```ts
`Connection: ${lastState}${stateDetail ? ` (${stateDetail})` : ""}`;
```

当前没有展示：

- 最后一次收到 QQ 入站消息的时间；
- 最后一次成功/失败出站的时间；
- 当前是否有 QQ agent run；
- 当前流式气泡状态；
- 心跳 ACK 年龄。

因此即使入站或出站已经失效，终端仍可能显示 `connected`。

### 3.4 短后台与长后台的差异

“短时间后台正常、长时间后台失败”把问题的主要变量指向手机端：

- **短时间后台**：QQ 进程仍在运行，或操作系统尚未冻结它；QQ 与服务器的连接仍在，机器人消息可以正常推送和显示。
- **长时间后台**：手机系统可能冻结或杀死 QQ 进程，QQ 进入离线状态；此时机器人发送的消息不会到达手机。重开后新消息仍能正常到达 pi（已确认）。
- 重新打开 QQ 后，客户端会重新连接并同步会话，但**离线期间由机器人产生的消息是否被保存/补发，取决于 QQ 平台和消息类型**。
- 普通聊天消息、机器人普通文本、机器人流式消息可能有不同的保存/补发策略。

电脑侧的 pi 一直在运行，只能证明“发送方正常”，不能证明“接收方在线”。HTTP 请求成功也不等于手机客户端最终展示了内容。

## 4. 已确认的代码与官方规则差异

### 4.1 C2C 被动回复窗口：代码 5 分钟，官方 60 分钟

官方规则（[消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)）：

- 单聊被动消息有效期：**60 分钟**；
- 每条消息最多回复 **4 次**；
- 主动消息可以被用户在 QQ 客户端关闭「允许主动发送」，关闭后主动消息发送失败。

当前代码：

```ts
// src/quota/reply-quota.ts:34
this.freshMs = opts?.freshMs ?? 5 * 60_000;
```

SDK 自带的 `ReplyLimiter` 默认 TTL 是 1 小时，与官方规则一致；pi-qq 额外设置的 5 分钟窗口是错误的。

影响范围需要精确区分：

- 流式消息始终携带原始 `msg_id`，不经过 `ReplyBudget.acquire()`，所以在 60 分钟内仍可能作为被动消息发送；
- 流式失败后的兜底文本、命令回复、附件失败提示会走 `sendReply`，超过 5 分钟后变成主动消息；
- 如果用户关闭了主动消息，这些内容会丢失，且只写本地日志。

### 4.2 流式消息没有普通文本兜底

`src/relay/bubble-writer.ts:207`：

```ts
this.pushedAny = true;
```

只要流式 HTTP 请求成功，就认为已经“推送过”。`run-stream-relay.ts:197` 返回成功后，`index.ts:247` 直接 `return`，不会再走 `sendReply`。

如果手机 QQ 在后台/离线期间没有收到流式帧，而 QQ 又没有为离线客户端保存或重放这些流式消息，那么重开手机后可能看不到任何内容；电脑侧却会记录发送成功。

官方流式消息文档没有承诺“接收方离线时保存/补发”，当前实现也没有做这个兜底。

### 4.3 `DONE` 帧内容为空

官方流式消息示例的最后一片：

```json
{
  "input_mode": "replace",
  "input_state": 10,
  "index": 2,
  "content_raw": "正在生成回答，请稍候。目前已完成全部内容，以下是最终结果。",
  "msg_id": "...",
  "stream_msg_id": "...",
  "msg_seq": 1
}
```

当前 `src/relay/stream-session.ts:121-123`：

```ts
const content = state === "done" ? "" : this.buffer;
```

即 `input_state=10` 的 `DONE` 帧发送空内容。虽然前面的 `generating` 帧已经发送过正文，但如果接收方离线、只看到最终状态，或 QQ 只保留 `DONE` 帧的内容，就可能表现为最终消息为空。

这一点需要和官方接口行为一起验证。

### 4.4 `event_id` 与 `msg_id` 同时发送

官方文档说明 `event_id` 和 `msg_id` 二选一：

- `event_id`：被动回复事件 ID；
- `msg_id`：被动回复消息 ID。

当前 `src/relay/stream-session.ts` 对 C2C 消息同时设置了：

```ts
event_id: this.msgId,
msg_id: this.msgId,
```

这是不符合接口约定的用法。虽然目前大多数情况下能发送成功，但可能导致平台按不同路径校验被动有效期或去重，需要纳入验证。

### 4.5 没有启用 session persistence

`src/qq/qq-bot.ts:33` 创建 `QQBot` 时没有传入 `sessionPersistence`。如果 pi 进程重启，无法 RESUME 之前的网关会话；长时间断线后，QQ 也只会对短时间重连补发遗漏事件（[事件订阅与通知](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/event-emit.html)）。

这与“电脑一直运行、没有重启”的本问题不是首要原因，但会影响进程重启场景。

## 5. 复现与证据

### 5.1 心跳 ACK 没有超时检测

本地用假网关复现：服务端发送 `HELLO` 和 `READY`，之后只接收心跳、不回 `HEARTBEAT_ACK`。700ms 后结果：

```json
{ "identifies": 1, "heartbeats": 13, "readies": 1, "disconnects": 0, "errors": 0, "serverCloses": 0 }
```

结论：客户端发了 13 次心跳、没有收到 ACK，但仍然保持连接，没有触发断线或重连。

相关代码：

- `node_modules/@tencent-connect/qqbot-nodejs/dist/protocol/gateway/gateway-connection.js:267`：`HEARTBEAT_ACK` 直接 `break`；
- 同文件 `:347-351`：心跳只检查 `ws.readyState === WebSocket.OPEN`。

这个缺陷在电脑休眠、网络切换时最容易触发；本次用户明确说电脑没有休眠/切网，所以优先级下降，但不能完全排除 NAT/网关侧静默失效。

### 5.2 没有事故日志

当前配置 `~/.pi/agent/pi-qq.json` 是：

```json
{ "logLevel": "debug" }
```

但在当前工作区及常见目录下没有找到 `pi-qq-*.log`。可能原因：

- 事故发生在其他 cwd；
- 日志被清理；
- 当时的 bot 尚未启动或运行在其他进程。

需要下一次复现时保留 `<cwd>/.pi/pi-qq/logs/pi-qq-YYYY-MM-DD.log`。

## 6. 可能原因

### P0：iPhone 后台挂起 QQ 网络，期间输出未送达/未补发

用户确认：

- iPhone；
- 失败时 TUI 一直有新事件，说明 agent 并非静默；
- 长后台后新消息能到 pi，且机器人有回复；
- 好友普通消息能在重开后同步。

最符合的解释：

1. iPhone 在长时间后台后挂起或断开 QQ 的网络；
2. 期间 pi 仍在正常产生并发送输出，但手机没有收到；
3. 重开后 QQ 恢复了实时连接，所以新消息有回复；
4. 但离线期间的机器人消息没有被 QQ 保存/补发，好友普通消息则可以同步；
5. 用户看到旧任务“完全没有消息”。

需要日志确认：失败期间 `stream`/`outbound` 是否显示发送成功。如果发送成功，问题在平台侧离线保存；如果流式失败/熔断，则同时存在 relay 问题。

### P0：没有“下次入站补发”机制

即使手机离线是外部原因，pi-qq 也没有在用户回来时补发状态或输出：

- 没有记录离线期间的任务进度/输出摘要；
- 下一次入站时不会先回报“上次任务仍在运行/已完成”；
- 用户只能看到新消息的回复，无法知道旧任务执行到哪一步。

这是当前最直接可改进的点，而且不依赖 QQ 是否保存离线机器人消息。

### P1：relay/stream 在长任务中停止推送

如果 TUI 在后台期间仍有新事件，但 QQ 没有对应消息，则要怀疑 relay/stream：

- 流式消息在 60 分钟 `msg_id` 有效期后失效，后续帧全部失败；
- `AppendStream` 熔断后 `streamDead = true`，中间内容不再推送；
- 只有最终 `message_end` 的兜底文本可能补发，而长任务可能迟迟不结束；
- 新消息的回复可能走了另一条 fallback 路径，所以看起来“有回复”，但旧任务的输出仍然丢失。

需要结合 `stream` 日志和 TUI 事件时间判断。

### P1：流式没有普通文本终态兜底

如果任务最终在手机离线期间结束：

1. 最终输出通过 `/stream_messages` 发出；
2. 手机离线，未收到最后几帧；
3. `streamTookOver === true`，pi-qq 不再发送普通文本；
4. 重开后可能只剩空记录。

即使当前失败时 agent 仍在运行，这个问题也会在任务结束时出现，因此仍需要处理。

### P1：5 分钟窗口导致兜底文本变成主动消息

仅影响“超过 5 分钟没有新入站消息”时的回复。如果用户重开后发了新消息，预算会重置；但如果用户只是等待之前任务的结果，或者流式失败后走兜底文本，就会被这个窗口影响。

### P2：入站 WebSocket 静默失效（已排除）

用户已确认长时间后台后新消息能到达 pi，且机器人有回复，因此入站和实时出站均已排除。保留此项仅因为当前没有心跳 ACK 超时检测，未来仍可能在电脑休眠/网络切换时发生。

### P2：长时间断线不补发

QQ 只保证短时间重连的 RESUME 补发；长时间离线或会话失效后，漏掉的 `C2C_MESSAGE_CREATE` 不会补发。如果 pi 进程重启过，也没有 `sessionPersistence` 可恢复。

### P3：手机 QQ 客户端设置

- 机器人会话被收纳/静音；
- 聊天窗口出现“灵魂不在线”提示；
- 用户关闭了「允许主动发送」；
- 手机系统限制 QQ 后台网络。

这些需要手机端现场确认。

## 7. 待确认的现场信息

复现时请记录：

1. **后台时长阈值**
   - 短时间后台（例如 1 分钟、5 分钟）是否正常；
   - 从多久开始失败（10 分钟、30 分钟、1 小时）；
   - 息屏与切到其它 app 是否有区别。
2. **重开后是否发送了新消息**
   - 新消息是否出现在电脑 pi 的 TUI；
   - 是否产生 `inbound message` 日志；
   - 机器人是否对这条新消息产生了 QQ 回复（而不只是 pi 收到）。
3. **聊天记录中是否有机器人历史输出**
   - 完全没有；
   - 只有部分气泡；
   - 有完整内容但时间不对。
4. **对照普通好友消息**
   - 长时间后台期间，好友发来的普通消息在重开后是否出现；
   - 如果普通消息能同步、机器人消息不能，问题更偏向机器人消息的保存/补发，而不是手机网络。
5. **QQ 聊天窗口是否有提示**
   - “灵魂不在线”；
   - “机器人暂时无法回复”；
   - 消息被折叠/收纳。
6. **任务进度（关键）**
   - 失败时 TUI 的 agent 是运行中还是 idle（当前已确认是运行中）；
   - 后台期间 TUI 是否仍出现新的 tool/assistant 事件；
   - 最后一条事件的时间和内容；
   - 当前工具名、已运行时长；
   - 是否长时间停在同一个工具/同一行；
   - `/qq-status` 和 `/qq-test-budget` 的输出。
7. **日志**
   - 最后一条 `gateway READY/RESUMED`；
   - 最后一条 `Dispatch event: t=C2C_MESSAGE_CREATE`；
   - `sent to pi`；
   - `stream` 相关日志；
   - `outbound` 相关日志和错误；
   - 最后一条 `agent_start` / `agent_end` / `tool` 事件。
8. **iPhone 设置**
   - 低电量模式是否开启；
   - QQ 的后台 App 刷新/后台网络权限；
   - 通知权限和机器人会话是否被收纳；
   - 长后台后是否出现“灵魂不在线”。

## 8. 建议的验证实验

### 实验 0：短后台 / 长后台对照

固定使用同一种消息类型（先只用 `/qq-test-md`），分别让手机后台：

- 1 分钟；
- 10 分钟；
- 30 分钟；
- 1 小时。

每次重新打开 QQ 后记录是否能看到消息。目标是找到从“正常”变成“收不到”的时间阈值，并确认息屏、切换 app、系统清理后台是否有差异。

### 实验 A：确认入站是否正常

1. 手机 QQ 后台放置足以复现问题的时间；
2. 重新打开，发送一条纯文本 `ping`；
3. 观察电脑 TUI 是否出现这条消息，以及日志是否有 `inbound message`。

结果：

- TUI 没有：入站链路问题；
- TUI 有、但手机没有回复：出站或 agent 问题。

### 实验 B：普通文本 vs 流式消息

在手机保持后台时，从电脑 TUI 依次触发：

```text
/qq-test-md bg-md-test
/qq-test-stream
```

同时在后台期间让一位好友发一条普通 QQ 消息作为对照。记录时间，然后重新打开手机 QQ，比较：

- 好友普通消息是否出现；
- `/qq-test-md` 的普通 Markdown 消息是否出现；
- `/qq-test-stream` 的流式气泡是否出现；
- 是否只有第一个气泡或空内容。

结果：

- 好友消息出现、机器人消息不出现：问题偏向机器人消息的离线保存/补发；
- 普通文本出现、流式不出现：高度怀疑流式消息离线不可见/未落盘；
- 两者都不出现：更偏向连接、主动消息或客户端问题；
- 两者都出现：原始问题不在出站，需要回到入站/任务状态排查。

### 实验 C：主动消息窗口

1. 从手机发一条消息，确保最后一次入站在 6 分钟前；
2. 不发送新消息，直接从 TUI 触发 `/qq-test-md active-window-test`；
3. 检查手机 QQ 是否收到，以及日志是否显示 proactive。

同时检查 QQ 机器人资料卡的「允许主动发送」开关。

### 实验 D：长任务流式结束

运行一个持续超过 5 分钟但少于 60 分钟的任务，手机保持后台，任务结束后重开，检查：

- 是否看到完整流式结果；
- 是否只有部分气泡；
- 日志中 `DONE` 是否成功、`stream` 是否报错。

### 实验 E：后台期间任务完成（关键）

这是最贴近原始现象的实验：

1. 手机在前台，从 QQ 发一条会执行约 2-3 分钟的任务；
2. 看到任务开始输出后，把手机 QQ 切到后台；
3. 在电脑 TUI 等待 `agent_end` / 任务完成，期间不打开手机；
4. 任务完成后，再打开手机 QQ，检查聊天记录。

对照组：同样任务，手机保持前台直到完成。

结果：

- 前台完成能看到、后台完成看不到：问题在任务结束时的最终输出/流式落盘；
- 后台完成也能看到：需要检查任务是否真的在后台期间结束，或是否存在特定的流式错误/主动消息限制；
- 两边都看不到：问题不在“后台”本身，回到 agent 执行或通用出站。

### 实验 F：长静默阶段对照（辅助）

用户已确认失败时 TUI 一直有新事件，因此本实验降为辅助，仅用于验证“没有事件时是否也没有消息”。

1. 在 QQ 发一个会执行长时间、期间没有输出的工具任务（例如一个运行 5-10 分钟的 `bash` 命令）；
2. 看到工具开始气泡后，把手机 QQ 切到后台；
3. 在电脑 TUI 观察工具是否仍在运行，记录最后事件时间；
4. 在工具未结束时重新打开手机 QQ，检查是否有新消息；
5. 再发一条新消息，确认机器人是否回复，以及回复是否与旧任务进度有关。

结果：

- TUI 没有新事件、QQ 也没有新消息：说明“运行中但静默”是正常行为，核心问题是缺少进度反馈；
- TUI 有新事件、QQ 没有：问题在 relay/stream；
- 新消息能回复、旧任务没有输出：进一步说明实时出站正常，旧任务只是没有可推送事件。

## 9. 解决方案

### 9.0 下次入站补发离线期间的状态/输出（推荐）

不依赖 QQ 是否保存离线机器人消息，改用“下一次入站”这条已经确认可用的通道：

- 记录最近一次/多次 QQ 任务的开始时间、状态、最后事件时间、当前工具和输出摘要；
- 下一次入站时，如果距上次入站超过阈值（例如 2 分钟）且期间有输出，先回复一条摘要，例如“你离开期间任务仍在运行/已完成；当前工具 bash，已运行 12 分钟；最近输出：……”；
- 提供 `/last` 命令：运行中重新推送当前输出；空闲时返回最近一次完成 run 的最终文本；不缓存完整历史；
- 摘要要限制长度，并标记“离线期间可能未送达”，避免与用户已看到的内容重复；
- 这是最可靠的“回来后知道执行到哪一步”的方案。

### 9.1 修复被动回复窗口（低风险，优先）

将 `src/quota/reply-quota.ts` 的默认窗口从 5 分钟改为 60 分钟，直接使用 SDK `ReplyLimiter` 的 TTL 或与官方规则一致：

```ts
this.freshMs = opts?.freshMs ?? 60 * 60_000;
```

同步更新：

- `test/quota/reply-quota.test.ts` 的 5 分钟断言；
- `/qq-test-budget` 的 `msgId window` 诊断；
- README 中的被动回复说明（如有）。

### 9.2 增加流式结束后的持久化兜底（需要产品决策）

可选方案：

1. **始终补发最终普通文本**：流式成功后，再发送一次完整最终文本或摘要。  
   优点：离线用户一定能看到一份持久内容；缺点：在线用户会看到重复内容。
2. **可配置补发**：新增 `streamFinalText` 配置，默认关闭或开启由用户决定。
3. **长任务补发**：只对超过某个时长或流式帧数超过阈值的任务补发普通文本。
4. **使用 `DONE` 帧携带完整内容**：验证 `input_state=10` 时发送完整 `content_raw` 是否能让离线客户端恢复内容。这是最接近协议示例的修复，但需要实测。
5. **下一次入站时补发状态/摘要**：记录每个任务的状态和最终结果；当检测到距上次入站超过阈值（例如 10 分钟）时，在下一次入站回复前先发送“上次任务已完成/仍在运行”的摘要。这样即使手机在任务运行期间离线，用户重新发消息后也能知道执行结果。

建议先做实验 B，再决定是否采用“始终补发”。

### 9.3 修正流式请求字段

- 验证 `DONE` 帧是否应携带完整内容；
- 验证 `event_id` 与 `msg_id` 同时发送是否被平台接受；
- 按官方约定，C2C 消息回复只使用 `msg_id`，不发送伪造的 `event_id`。

### 9.4 出站失败可恢复

当前 `src/qq/reply-sender.ts` 在被动发送失败后只尝试一次主动发送；主动失败后仅写日志。建议：

- 增加待发送队列，保存失败内容；
- 在下一次入站消息到来时，以被动消息补发；
- 或者提示用户“有一条回复发送失败，请重试”；
- 日志中记录明确的失败原因，供 `/qq-status` 展示。

### 9.5 增强状态面板

在 `getStatusLines` 中增加：

- `Last inbound`: 最后一条 QQ 消息时间；
- `Last outbound`: 最后一条发送结果（成功/失败/主动降级）；
- `Last task`: 最后一次 QQ 任务的状态（运行中/完成/失败）和结果摘要；
- `QQ run`: `runFeedback.isQQRunActive()`；
- `Stream`: 当前是否有活跃气泡、是否已熔断；
- `Gateway`: 最后 `ready/resumed/disconnected` 时间；
- 如能扩展 SDK，增加心跳 ACK 年龄。

终端 `/qq-status` 和 QQ `/status` 共用这些字段。这样即使手机收不到消息，用户也能从电脑端判断执行状态。

### 9.6 运行中进度反馈（当前最直接的改进）

当前失败场景是“agent 仍在运行，但没有可推送事件”。可以增加运行中的显式状态：

- `RunFeedback` 记录 `runStartedAt`、`lastEventAt`、`currentTool`、`currentStep`；
- 每次 tool/assistant 事件更新 `lastEventAt`；
- 定时检查：如果 run 仍活跃，且 `now - lastEventAt` 超过阈值（例如 5 分钟），发送一次状态消息，例如“⏳ 仍在执行：bash，已运行 12 分钟”；
- 下一次入站消息到达时，如果距上次入站/事件超过阈值，先回复“上次任务：运行中/已完成，当前工具…，已运行…”，再处理新消息；
- `/status` 和 `/qq-status` 展示同样的字段。

注意：

- 状态消息优先使用当前 `msg_id` 作为被动回复；超过 60 分钟后可能只能走主动消息；
- 应设置阈值并限制“每次静默期只发一次”，避免刷屏；
- 这是解决“无法判断执行状态”的直接手段，但不能修复真正的流式投递丢失。

### 9.7 SDK 心跳 ACK 超时（中期）

在 `qqbot-nodejs` 的 `GatewayConnection` 中：

- 记录 `lastHeartbeatAckAt`；
- 收到 `HEARTBEAT_ACK` 时更新；
- 心跳定时器检查 `now - lastHeartbeatAckAt > 2 * heartbeat_interval`；
- 超时后 `cleanup()` + `planReconnect()`，用 RESUME 恢复；
- 增加假网关测试：服务端停止 ACK 后必须触发重连。

这是入站链路的根本性加固，即使本次不是首要原因，也建议后续处理。

### 9.8 session persistence（可选）

为 `QQBot` 传入文件型 `sessionPersistence`，让 pi 进程重启后可以尝试 RESUME。注意：

- 长时间离线仍可能被平台判定 session 失效；
- 需要和 QR 登录/凭据生命周期一起设计；
- 不能解决手机离线期间消息不补发的问题。

## 10. 建议执行顺序

1. **先确认发送侧是否成功**：查失败期间 `stream`/`outbound` 日志，区分“消息已发送但手机离线未保存”和“relay/stream 停止推送”。
2. **实现下次入站补发 + 运行中进度反馈**：记录最近任务状态/输出摘要，用户回来发消息时先回报；这是当前最直接解决“无法判断执行状态”的改动，且不依赖 QQ 离线保存。
3. **修复 60 分钟窗口**：低风险、确定性高。
4. **决定是否补发最终普通文本**：流式结束后保留一份持久化终态；需要先验证 QQ 是否保存离线普通机器人消息。
5. **验证 `DONE` 内容与 `event_id` 字段**：需要真实 QQ 客户端配合。
6. **增强状态面板**：展示最后入站、最后出站、当前/最后一次任务状态。
7. **增加出站失败队列**：改善出站失败后的可恢复性。
8. **修 SDK 心跳 ACK 超时**：作为入站可靠性加固。
9. **评估 session persistence**：仅针对进程重启场景。

## 13. 实现记录：`/last`

已实现第一版 QQ 侧 `/last` 命令，不缓存完整对话历史。

### 行为

只保留两种状态：

- **pi idle（已完成）**：返回最近一次完成 run 的最终 assistant 文本；
- **pi 运行中（未完成）**：重新开始推送当前 run 的最新文本，创建一个新的流式气泡；后续 delta 继续写入这个新气泡。

边界情况：

- 运行中但还没有文本：不额外回复，等下一次可推送输出；
- idle 且没有完成的文本：回复 `No completed message yet.`；
- 重新推送只保证“当前文本 + 后续输出”，不保证补齐离线期间已经错过的所有历史气泡。

### 实现

- `src/relay/bubble-writer.ts`
  - 新增 `restartText(text)`：关闭当前气泡（如仍有内容），重置流状态并创建新气泡，重新推送当前文本；流式已熔断时也会尝试恢复。
- `src/relay/run-stream-relay.ts`
  - `RunState.currentText` 保存当前 run 的最新文本；
  - `lastCompletedText` 保存最近一次完成 run 的最终文本；
  - `getLastMessage()` 只返回最近完成文本；
  - `repushCurrent()` 在运行中重新推送当前文本；不重写 `resultSentLen`，避免下一条 assistant 消息的开头被截掉；
  - 流式已经熔断时仍更新 `currentText`，因此 `/last` 不依赖 stream 状态。
- `src/qq/inbound-command.ts`
  - 用 `ctx.isIdle()` 分成两种状态；
  - 运行中直接调用 `restartPush()`，不额外回复；
  - idle 调用 `getLastMessage()` 并返回最终文本。
- `index.ts`
  - 接入 `runFeedback.getLastMessage()` 和 `runFeedback.repushCurrent()`。
- 测试：
  - `test/relay/run-stream-relay.test.ts` 覆盖重新推送、最终文本和流式熔断；
  - `test/qq/qq-message-handler.test.ts` 覆盖两种状态和静默边界。

### 限制

- 只保留 assistant 文本，不包含 thinking/tool 历史；
- 重新推送会把当前文本再发一次，手机上可能看到重复内容；这是手动恢复行为；
- 如果超过 60 分钟被动窗口或流式已经不可恢复，重新推送仍可能失败；
- 最近一次 run 如果没有文本，会清空 `lastCompletedText`；
- 非 QQ 触发的本地 run 不在 `RunFeedback` 中，`/last` 可能只显示上一条 QQ 结果。
