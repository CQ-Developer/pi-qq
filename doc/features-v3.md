# pi-qq — features-v3.md

> V3 增量：F12 直推式过程回传（取代 v1 F7 的窗口汇总）、F13 移除消息心跳、F14 配置项收敛。
> 基线见 [features-v1.md](./features-v1.md) 与 [features-v2.md](./features-v2.md)；本文只描述新增/变更。
> 状态：F12 / F13 / F14 已实现；2026-11-02 主链路真机复验通过；按内容块切泡真机运行成功（30 泡 / 16 次工具、全部 200）。已定位短思考泡 unsupported 的根因是单行引用块，改为在每个思考泡末尾补空引用行；工具行改为 ``*[<name>]* `<主参数>` `` 且每个工具调用独立成泡，待真机复验。

## 1. 背景与结论

v1 F7 采用「固定窗口汇总帧」：思考只留 `[💭] Thinking...` 标记，工具合并成 `[🔧] [n] name` 计数，文本增量按 `streamFlushMs` 合帧。长任务实测暴露出三个问题：

- 用户看不到实际思考内容，只能看到「思考中」；
- 工具调用被计数合并，失去单次调用的时序；
- 汇总窗口天然引入最多一个 `streamFlushMs` 的延迟，且为「保活」又叠加了消息心跳与两个配置项。

V3 的方向是**事件直推**：思考内容、工具调用（含参数与结果）、assistant 文本在事件到达时按顺序直接追加，不再生成汇总消息；同时删除心跳和冗余配置。

已定决策：

1. **回传思考内容**（变更 v1 决策 #2）：以 Markdown 引用块输出原文；新增 `thinkingRelay`（默认 `true`）作为隐私/降噪开关。
2. **逐次回传工具调用**（变更 v1 决策 #3）：每次调用一段，包含参数与结果；不再合并计数。
3. **取消窗口汇总与消息心跳**：过程可见性由直推时间线承担。
4. **收敛配置项**：删除 `streamFlushMs`、`streamAssistant`、`streamRelay`、`markdownSupport`、`heartbeatMinutes`、`heartbeatMaxMessages`；新增 `thinkingRelay`。

## 2. F12 直推式过程回传

### 2.1 目标

QQ 侧看到的时间线与 pi 事件顺序一致，没有汇总延迟、没有计数合并、没有「思考中」占位；工具的参数与结果可追溯。

### 2.2 目标输出

````text
> 思考内容
> 思考内容

*[bash]* `npm test`
```text
12 passed
```

> 思考内容
> 思考内容

*[read]* `src/foo.ts`
```text
export function foo() {
  return 1;
}
```

message

> 思考内容

*[bash]* `exit 1`
```text
❌ command failed with exit code 1
```

message
````

- `message` 为 assistant 文本增量（原文，不额外包裹）。
- **每个内容块独立气泡**：思考块一个泡、工具调用+结果一个泡、文本块一个泡；按时间顺序连续出现，块与块之间不再靠空行分隔。
- 工具段由「起始行 + 结果代码块」组成：起始行是 ``*[<name>]* `<主参数>` ``，结果在紧随其后的 `text` 代码块中。
- 成功结果不加前缀；失败结果在代码块首行加 `❌ `，不额外加标记行。
- 代码块在 `tool_execution_end` 时一次性追加，保证围栏完整；内容含 ``` 时自动加长围栏。
- 单个块超过 12,000 字符时，若处于安全边界（行首、围栏已闭合、无 `pendingResume`），主动结束当前泡并在该块内新建下一泡；工具起始行与结果不拆开。
- 示例中的具体参数/结果是占位；真实内容按 §2.4 截断。

### 2.3 事件映射

| pi 事件                            | 输出                                     |
| ---------------------------------- | ---------------------------------------- |
| `message_update`（thinking 快照）  | 思考增量，按行加 `> `（`thinkingRelay`） |
| `message_update`（text 快照）      | 文本增量，原文追加                       |
| `tool_execution_start`             | ``*[<name>]* `<主参数>` ``               |
| `tool_execution_end`               | `text` 代码块（失败首行加 `❌ `）        |
| `message_end`                      | flush 缓冲；决定该消息是否由消息路径接管 |
| `agent_end`                        | 收尾 flush + DONE                        |
| `agent_start` / `session_shutdown` | 开泡 / 清理，沿用 v1                     |

### 2.4 行为规则

- **顺序**：严格按事件到达顺序追加；不合并同名工具、不跨事件重排。
- **思考**：
  - `message_update` 给的是累计快照，按差量追加，不重复发送已推送部分；
  - 每行前缀 `> `；块内空行输出 `>` 以保持引用块连续；
  - `message_end` 重置差量基准，下一条消息重新开始；
  - `thinkingRelay: false` 时完全不输出思考内容，也不输出占位标记；
  - 不回传思考元数据，只回传正文。
- **工具**：
  - `tool_execution_start` 追加 ``*[<name>]* `<主参数>` ``；
  - `tool_execution_end` 追加一个 `text` 代码块；失败时首行加 `❌ `；
  - **主参数**：`args` 为字符串时直接使用；为对象时按 `command` → `path` / `file_path` / `filename` → `pattern` / `query` / `url` 的顺序取第一个字符串字段；都不命中时用紧凑 JSON。`bash` 即 `args.command`，所以显示为 `` *[bash]* `npm test` ``；
  - 参数换行替换为空格，上限 200 字符；参数用行内代码包裹；
  - 结果从工具结果的 `content[].text` 提取；无文本时取 `structuredContent`（字符串或 `.output`）；避免显示 wrapper JSON；
  - 结果上限 600 字符 / 8 行，超出以 `…` 结尾；
  - 结果代码块的围栏长度按内容中最长反引号串 +1 决定（至少 3），避免结果中的三反引号提前关闭；
  - 空结果输出 `(no output)`；空失败输出 `❌ (no output)`；
  - 每个工具调用单独一个气泡；并行发起的工具按开始顺序逐个展示，结果通过 `toolCallId` 归属，不会错配；
  - 工具起始行与结果始终在同一气泡；结果返回前不切泡；
  - 后一个并行工具的起始行会等前一个工具完成后才发送，避免多个流同时打开。
- **文本**：流式原文增量；与 v1 相同，流式帧按 Markdown 渲染。
- **排版**：同一气泡内相邻同类内容连续追加；块类型切换时结束当前气泡并新建气泡，不在新泡开头补空行。
- **气泡**：按时间顺序，每个内容块一个气泡。思考块、每个工具调用、文本块各自独立；块切换时结束当前泡并新建下一泡。单个块内累计达到 `MAX_BUBBLE_CHARS` = 12,000 后，仅在安全边界（行首、围栏已闭合、无 `pendingResume`、无进行中的工具）主动切泡。每个思考泡结束时保证至少有一个空引用行（`>`），避免 QQ 把单行引用块显示为 `该消息类型暂不支持查看`。
- **节流**：没有应用层窗口；仅保留 `AppendStream` 的 500ms 合并与平台 300ms 下限。也就是说「直推」指语义上逐事件，不承诺每个 token 一帧。
- **失败与续写**（clean resume 已实测通过）：
  - `AppendStream` 内部对 429 / 50002 退避重试（最多 3 次）；
  - **同泡续写**：保存检查点（`stream_msg_id`、`msg_seq`、下一个 `index`、未确认缓冲），失败后用同一 `stream_msg_id` 与下一个 `index` 重发；最多 2 次；续写仍失败 → `streamDead`；
  - `index` 每次发送尝试后递增（平台要求递增）：失败帧的未确认缓冲用下一个 `index` 重发；若平台已接收该帧，可能产生重复；
  - 实测记录：frame 1 后丢弃客户端对象，用同一 `stream_msg_id` + 下一个 `index` 发送 frame 2，QQ 仍在同一气泡；
  - 失败后续写、重复/跳号 `index`、5 分钟后续写仍待真实故障验证；若后续实测同泡续写不可用，再回退新建气泡（最多 1 次，v3 当前不启用）；
  - 已确认显示的内容不补发；失败帧的未确认缓冲随续写重发（若平台已接收则可能重复）；`streamDead` 后停止过程推送，`onWarn` 只提示一次；
  - `message_end` 先 flush 当前缓冲；若 flush 失败或已 `streamDead` → 该消息返回「未接管」，由消息路径发送**完整文本**；可能重复已显示的部分，优先保证完整；
  - 块切换时若有未闭合围栏，先按原引用状态补发闭合围栏（思考内的围栏补 `> ` 前缀），防止后续工具/文本被吞进代码块；切泡要求围栏已闭合；
  - 已知限制：失败帧若已被平台接收但客户端未收到确认，重试可能重复；反向则可能丢一帧。
- **结束**：`agent_end` flush 剩余内容并 DONE；`message_end` 本身不封泡。
- **不发送**：开始确认、用量摘要、消息心跳。

### 2.5 不做

- 工具耗时；
- 思考内容脱敏、逐块折叠；
- 每个 token 单独一个气泡，或把工具结果从调用行拆成两个气泡；
- 进程内持久化时间线。

### 2.6 验收

- 单轮任务：思考块、工具段、文本各自成泡，顺序与 pi 事件顺序一致，无汇总延迟。
- 多轮任务：文本之后的新思考/工具继续新建气泡，不重发旧内容。
- 切块：每个工具调用一个泡；并行工具按开始顺序逐泡展示；工具起始行与结果不分离。
- 思考快照：同一块只输出一次，无重复、无截断；跨消息重置正确；`thinkingRelay: false` 时完全静默。
- 工具：N 次调用 N 个泡；命令与结果可见且按 `toolCallId` 配对；成功/失败代码块正确；截断与围栏自适配生效；无 `[n]` 计数。
- 续写：clean resume 同一气泡；失败后用下一个 `index` 重发，最多 2 次；失败后停止过程推送，最终文本仍完整送达，warn 只出现一次。
- 超长块：超过 12k 字符后按安全边界切泡，多泡内容连续、无重复/丢失；切点处围栏闭合，工具参数行与结果不被拆开。
- 单行思考：思考泡末尾自动补 `>` 空引用行，不再出现 `该消息类型暂不支持查看` 的占位消息。
- `streamDead` 后的 assistant 消息走消息路径，不出现空泡。
- 旧气泡停在半截属于已知限制，不尝试撤回。

## 3. F13 移除消息心跳

### 3.1 结论

删除 `heartbeatMinutes` / `heartbeatMaxMessages`、心跳定时器、`beat()`、`formatHeartbeat`、工具总计与 `onToolEnd`；只保留 typing 保鲜。

### 3.2 依据

| 问题           | 说明                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| 默认路径不可达 | v1 的 `streamRelay` 默认 `true`，`beat()` 首行即返回；定时器每 10 分钟空转一次 |
| 兜底名不副实   | 判据是配置开关而非链路健康；流真实失败不会翻转开关，也没有 run 级 dead 状态    |
| 成本           | 10 分钟时已超出 `msgId` 的 5 分钟被动窗口，会消耗主动消息额度；typing 免费     |
| 覆盖不足       | 10 分钟间隔 × 最多 3 条只覆盖前 30 分钟，60 分钟任务后半程仍然静默             |
| 语义冲突       | v1 的 `streamRelay: false` 定位为「关闭时间线」，心跳却仍在发消息              |

### 3.3 行为变化

- 删除后：过程可见性完全由 F12 承担；流不可用（`streamDead`）时只有 typing + 最终消息。
- 旧配置键被静默忽略（与已移除的 `usageRelay` 一致），不报错、不写回。
- 代码、测试、README、`features-v1.md` 同步删除相关内容。

### 3.4 现状

工作区已实现（未发布）：`src/run-feedback.ts`、`src/config.ts`、`index.ts`、测试与文档均已同步。

## 4. F14 配置项收敛

| 配置                   | v3 处置    | 说明                                                                                 |
| ---------------------- | ---------- | ------------------------------------------------------------------------------------ |

| `streamRelay`          | 删除       | 过程推送成为唯一默认路径；失败由同泡续写 + `streamDead` 熔断处理，不再提供手动总开关 |
| `streamFlushMs`        | 删除       | 无窗口汇总；节流固定在 `AppendStream`（500ms，平台下限 300ms）                       |
| `streamAssistant`      | 删除       | 从未被读取的死配置，只存在于定义与默认值                                             |
| `heartbeatMinutes`     | 删除       | F13                                                                                  |
| `heartbeatMaxMessages` | 删除       | F13                                                                                  |
| `markdownSupport`      | 删除       | 流式帧天然按 Markdown 渲染；非流式路径统一转纯文本，不再依赖机器人权限配置           |
| `deliverAs`            | 保留       | 与回传无关                                                                           |
| `imageMaxSize`         | 保留       | 与回传无关                                                                           |
| `fileMaxSize`          | 保留       | 与回传无关                                                                           |
| `logLevel`             | 保留       | v2 既有                                                                              |
| `debug`                | 仅迁移读取 | v2 既有（`debug: true` → `logLevel: "debug"`）                                       |

**删除 `streamRelay` 的影响**

- 所有 run 都会尝试流式推送；平台不支持时由 `streamDead` 熔断，最终文本仍通过消息路径送达。
- 不再有「只想收最终消息」的全局开关；降噪只能关闭思考（`thinkingRelay: false`）。这是 V3 的明确取舍。
- 发布前用 `/qq-test-stream` 验证流式帧渲染；失败则回滚这一项。
- 每个内容块一个气泡（思考块、每个工具调用、文本块分别独立；并行工具按开始顺序逐泡展示）；单个块超过 12k 后按安全边界切泡；续写不新增气泡。

**删除 `markdownSupport` 的影响**

- 流式帧固定 `content_type=MARKDOWN`，无需权限配置；主路径天然支持 Markdown。
- 非流式路径（`streamDead` / 最终文本回退）统一走 `markdownToPlain` + 纯文本 `msg_type`：不依赖机器人权限，保证任何租户都能读。
- `QQBot` 不再传 `markdownSupport`，`sendText` 固定为纯文本；代价是回退时失去标题/列表/代码的富文本样式。
- `/qq-test-md` 诊断命令保留，用于单独验证平台的 Markdown 发送能力，不再与配置项绑定。
- 风险：若某个租户的流式帧实际不渲染 Markdown，已无配置可关；只能真机验证并在必要时回滚（见 §6）。

迁移规则：

- 已删除键（`streamFlushMs`、`streamAssistant`、`streamRelay`、`markdownSupport`、`heartbeatMinutes`、`heartbeatMaxMessages`）出现在旧配置中时静默忽略；不写回、不报错。
- 旧配置 `streamRelay: false` / `markdownSupport: true` 的用户升级后行为变化写入发布说明。

## 6. 风险

- **msgId 新鲜度与续写**：clean resume 已通过；现有气泡能否持续追加、失败后续写是否被接受、10–60 分钟任务后半程是否可续写，仍需真机验证。
- **`streamRelay` / `markdownSupport` 删除后的回退面**：平台拒绝流式、用户不希望过程推送、或流式 Markdown 不渲染时，没有手动开关；只能依赖熔断 + 纯文本消息路径。发布前用 `/qq-test-stream` 验证；必要时回滚这两项配置。
- **续写的配额**：同泡续写不新增气泡；最终消息可能接近每个 `msgId` 约 4 条的被动上限，需在 `/qq-test-budget` 观察。
- **气泡数量与额度**：每个内容块一个泡会显著增加消息数；71k 实测 run 有 34 次工具调用，若全部顺序执行约生成 34 个工具泡。2026-11-02 按块真机 run 共 30 个泡（16 次工具），全部 API 200；短思考泡曾显示 `该消息类型暂不支持查看`。诊断确认根因是单行引用块，已改为思考泡末尾补空引用行，待复验。若额度或刷屏不可接受，回退为「每个 run 一个过程泡 + 最终答复单独泡」。
- **单块长度/帧数**：直推会显著增加帧数。2026-11-02 真机实测约 15k 字符后平台自动切出第二泡（`stream_msg_id` 不变），71k 任务的 157 帧中还有 11 帧起始处于未闭合围栏内，切点不可控。单个块内仍保留 12k 主动切泡；平台是否接受新泡、切点排版与内容连续性仍需真机复验。2026-11-02 复验：9.3k 字符单泡正常。
- **主动切泡的连续性**：新泡复用同一 `msgId` 但不带旧 `stream_msg_id`；若平台把新泡当成新消息而不是同一 run 的延续，需要回退为「平台自动切分」或调整阈值。
- **围栏补闭合**：思考内嵌围栏补 `> ` 前缀可能与模型原始围栏风格不完全一致；若平台渲染仍异常，需改为切泡前截断或转义围栏。
- **index 单调递增**：真机已报错「请求参数index需要递增」；失败帧必须用下一个 `index` 重发，不能复用。
- **参数/结果体积与隐私**：工具参数和结果可能包含文件内容、路径、密钥片段；已做字符/行截断，但仍会进入 QQ 聊天记录。仅回传给绑定用户。
- **并行工具**：当前按开始顺序串行展示，前一个工具完成前不出后一个工具泡；极长工具会延迟后续工具可见性。
- **噪音**：长思考与长结果会刷屏；`thinkingRelay` 只能关思考，工具与文本仍会推送。
